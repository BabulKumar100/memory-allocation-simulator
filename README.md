# Memory Allocation Simulator

An interactive, full-stack simulator for operating-system memory management. It lets you define memory partitions and a queue of processes, run any of the four classic contiguous allocation algorithms step by step, and see exactly where every process lands, how much memory is still free, and which processes could not be placed.

The project is built on the MERN stack (MongoDB is optional) and is designed as a teaching tool: every number shown in the interface comes from a single, documented calculation path, so what you see on screen is what the algorithm actually did.

## Overview

Memory allocation is the problem of placing processes of varying sizes into available memory partitions. Different algorithms make different choices, and those choices lead to noticeably different results: one algorithm may place every process, while another leaves a large process waiting even though enough total memory exists.

This simulator makes that difference visible. You switch algorithms, run the same workload, and compare the outcome directly through the visualization, the statistics, and the allocation table. A `Step` control lets you replay the allocation one process at a time instead of only seeing the final state.

Two ideas are deliberately kept separate in the implementation:

1. **The allocation engine** decides which block receives which process. It lives in one shared module used by both the server and the client.
2. **The interface** only renders the result of that engine. It never re-implements the algorithm, so the numbers on screen can never drift from the actual logic.

## Features

### Simulation Control
- **Start** runs the selected algorithm against the current workload.
- **Reset** clears the result and returns to the initial state.
- **Step navigation** (previous / next / Finish) replays the allocation one process at a time. Every step is a complete snapshot of memory and metrics at that moment, generated by the server, so stepping backward is exact rather than recomputed.
- Changing the algorithm or editing the workload invalidates the previous result, preventing stale comparisons.

### Process Queue
- Add processes by size in KB; remove any process with the trash button.
- Process identifiers are re-sequenced automatically (`P1`, `P2`, …) after removal, so the queue never shows gaps.
- A minimum of 1 and a maximum of 20 processes are enforced, with the same limits validated on the server.

### Memory Partitions
- Add memory blocks by size in KB; click a chip to remove it.
- Block identifiers are likewise re-sequenced (`Block 1`, `Block 2`, …).
- Between 1 and 20 blocks are allowed, matching the server-side validation.

### Memory Visualization
- Every block is drawn as a vertical region whose width is proportional to its size, so a 600 KB block is visibly three times wider than a 200 KB one.
- Inside each block, each allocated process and any leftover space are drawn as proportional segments, which makes fragmentation immediately obvious.
- A percentage label on each block shows how full it currently is.
- The legend distinguishes three states: **Empty** (nothing allocated), **Allocated** (occupied by a process), and **Free / Remaining** (space still available).

### Live Statistics
- **Allocated Processes** — how many of the processes handled so far were placed successfully.
- **Allocation Success Rate** — the percentage of handled processes that were placed.
- **Memory Utilization** — allocated bytes as a share of total memory.
- **Free Memory** — total memory that is still available for allocation.

### Failed Processes
If any process cannot be placed, a dedicated panel lists each one with the size it required and the size of the largest free block that existed at that moment. This turns a silent failure into an understandable one: you can see precisely why the process did not fit.

### System Logs
A timestamped event log records every meaningful action — processes and blocks added, simulations started, resets, and API failures. The newest entry appears first and the list is capped at the 30 most recent events.

### Allocation Results
- A table showing, for each process, its size, the block it was placed in, the remaining space in that block after placement, and its status.
- When you are replaying a simulation step by step, the table reflects the state at the step you are viewing rather than only the final outcome.
- **Export CSV** downloads the result set as a spreadsheet-ready file, with values correctly quoted and escaped.

### Local Fallback
If the backend cannot be reached, the client runs the identical allocation module locally instead of failing. The interface stays usable for demonstration purposes, and the result is guaranteed to match what the server would have produced, because both use the same file.

## Allocation Algorithms

All four algorithms share the same filtering step: they first collect only the blocks that have at least as much free space as the process needs. They differ solely in which of those eligible blocks they choose. Each algorithm therefore reduces to a scoring rule, and the eligible block with the lowest score wins.

| Algorithm | Selection rule | Characteristics |
|---|---|---|
| **First Fit** | The first eligible block in memory order | Fastest to compute, but tends to leave many small unusable gaps near the start of memory |
| **Best Fit** | The eligible block with the smallest remaining space | Produces the smallest leftover fragments, though those fragments are often too small to be useful |
| **Worst Fit** | The eligible block with the largest remaining space | Leaves the largest possible remainder after each allocation, hoping it stays useful for later processes |
| **Next Fit** | The first eligible block found when searching forward from the position after the previous allocation, wrapping around to the start | Behaves like First Fit but avoids rescanning from the beginning each time, which spreads allocations more evenly |

### Next Fit is not the same as First Fit

Next Fit remembers where the previous allocation happened and resumes its search from the following block, wrapping to the beginning when it reaches the end. In many workloads the two produce identical results, but they diverge as soon as memory is fragmented near the start. Consider blocks of `300, 500, 400` KB with processes of `400, 90` KB:

- **First Fit** places the first process in block 2 and then scans from the very beginning, placing the second process in block 1.
- **Next Fit** places the first process in block 2, resumes from block 3, and therefore places the second process in block 3.

### A comparison example

The simulator ships with a classic textbook workload — partitions of `100, 500, 200, 300, 600` KB and processes of `212, 417, 112, 426` KB — which demonstrates how much the choice of algorithm matters:

| Process | First Fit | Best Fit | Worst Fit | Next Fit |
|---|---|---|---|---|
| 212 KB | Block 2 | Block 4 | Block 5 | Block 2 |
| 417 KB | Block 5 | Block 2 | Block 2 | Block 5 |
| 112 KB | Block 2 | Block 3 | Block 5 | Block 2 |
| 426 KB | not allocated | Block 5 | not allocated | not allocated |
| **Utilization** | 43.6% | **68.6%** | 43.6% | 43.6% |
| **Success rate** | 75% | **100%** | 75% | 75% |

Here Best Fit wins decisively: by consuming the smaller blocks first, it keeps the 600 KB block intact for the 426 KB process. Run the same workload through the other three algorithms in the simulator to see the difference for yourself.

## Allocation Model

The simulator models **variable partitioning**. Each listed partition is tracked as a separate region with a running `remaining` counter:

```
remaining = previous remaining − allocated process size
```

A process may be placed in a block as long as that block still has enough free space, which means leftover space inside a partially filled block remains available to later processes. This is why the interface labels that space **Free / Remaining** rather than *wasted* — it is genuinely reusable, and the example table above shows a process returning to a block that was already partly used.

If you need to model **fixed partitioning** instead, where a partition becomes unavailable once it is assigned, the eligibility test would change from "does this block still have enough free space" to "is this block unused", and the leftover space would need to be reported separately as internal fragmentation.

## Metrics and Calculations

All statistics are produced by the shared engine and are recomputed after every process, so the values you see while stepping are historically accurate rather than derived from the final state.

| Metric | Calculation |
|---|---|
| `totalMemory` | Sum of all block sizes |
| `usedMemory` | Sum of the sizes of all processes currently allocated across all blocks |
| `freeMemory` | `totalMemory − usedMemory`, which always equals the sum of all blocks' remaining space |
| `utilization` | `usedMemory / totalMemory × 100`, rounded to one decimal place |
| `allocatedProcesses` | Number of processes placed successfully so far |
| `processedProcesses` | Number of processes handled so far |
| `successRate` | `allocatedProcesses / processedProcesses × 100`, rounded to one decimal place |
| `failedProcesses` | The identifiers and sizes of every process that could not be placed |
| `largestFreeBlock` | Recorded for each failed process: the largest free block at the moment it failed |

Division by zero is guarded throughout, so an empty workload reports zeroes rather than failing.

Each process produces one **step** containing a full snapshot of memory, the allocation table up to that point, and the metrics above. The number of steps therefore equals the number of processes, which is what the step counter displays.

## Getting Started

### Prerequisites

- Node.js 18 or newer (Node 20 LTS or 22 recommended)
- npm
- A MongoDB connection string only if you want saved history

### 1. Start the backend

```bash
cd server
npm install
cp .env.example .env
npm run dev
```

The API starts on `http://localhost:5000`. You can confirm it is running with:

```bash
curl http://localhost:5000/api/health
```

The simulation endpoint works without any database. MongoDB is only needed for the saved-history endpoints, and the server prints a notice at startup when it is not configured.

### 2. Start the frontend

Open a second terminal:

```bash
cd client
npm install
cp .env.example .env
npm run dev
```

Open `http://localhost:5173` in your browser.

Both servers should be running to exercise the full stack. If the API is unavailable, the interface still works using the local fallback described above.

## API Reference

### `GET /api/health`

Returns a simple liveness check.

```json
{ "status": "ok", "service": "Memory Allocator API" }
```

### `POST /api/simulate`

Runs a simulation and returns the full result. This endpoint requires no database connection.

**Request**

```json
{
  "algorithm": "firstFit",
  "blocks": [
    { "id": "Block 1", "size": 100 },
    { "id": "Block 2", "size": 500 },
    { "id": "Block 3", "size": 200 },
    { "id": "Block 4", "size": 300 },
    { "id": "Block 5", "size": 600 }
  ],
  "processes": [
    { "id": "P1", "size": 212 },
    { "id": "P2", "size": 417 },
    { "id": "P3", "size": 112 },
    { "id": "P4", "size": 426 }
  ]
}
```

`algorithm` must be one of `firstFit`, `bestFit`, `worstFit`, or `nextFit`. Between 1 and 20 blocks and between 1 and 20 processes must be supplied, and every size must be a positive number. Invalid input returns HTTP 400 with a descriptive message.

**Response** (abridged)

```json
{
  "algorithm": "firstFit",
  "totalMemory": 1700,
  "usedMemory": 741,
  "allocations": [
    {
      "processId": "P1",
      "processSize": 212,
      "blockId": "Block 2",
      "remainingInBlock": 288,
      "allocated": true,
      "largestFreeBlock": null
    }
  ],
  "steps": [
    {
      "processId": "P1",
      "allocations": [],
      "memory": [
        { "blockId": "Block 1", "size": 100, "allocated": [], "remaining": 100 }
      ],
      "metrics": {}
    }
  ],
  "summary": {
    "allocatedProcesses": 3,
    "processedProcesses": 4,
    "failedProcesses": [{ "processId": "P4", "processSize": 426 }],
    "successRate": 75,
    "freeMemory": 959,
    "utilization": 43.6
  }
}
```

- `allocations` reports the final state of every process.
- `steps` contains one entry per process, each holding the memory snapshot and metrics at that point in time.
- `summary` is the metric set for the last step.
- `largestFreeBlock` is populated only for processes that failed to allocate.

### History endpoints

These endpoints require a configured `MONGODB_URI`. Without a database connection they respond with HTTP 503.

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/api/simulations` | Lists the 50 most recent saved simulations, newest first |
| `POST` | `/api/simulations` | Saves a simulation result |
| `DELETE` | `/api/simulations/:id` | Deletes a saved simulation by identifier |

## Architecture Notes

### One engine, two consumers

The allocation logic lives in exactly one file, `server/shared/allocation.js`, which exports the algorithm list, display labels, validation limits, the payload validator, and the simulation engine itself.

- The **server** imports it directly to serve `POST /api/simulate`.
- The **client** imports the very same file through the `@shared` alias configured in `client/vite.config.js`, which is used both for input validation limits and for the offline fallback.

This was a deliberate choice over keeping two copies of the algorithm. Duplicate implementations inevitably drift, and a subtle divergence — a differently rounded percentage, for instance — produces bugs that are hard to notice because both sides look plausible in isolation. Sharing the module makes consistency structural rather than something that has to be tested for.

The module is deliberately free of dependencies: no Node-specific APIs, no browser APIs, no build-time syntax. That is what allows the same file to run under Node and inside the browser bundle.

### Why the shared module lives inside `server/`

The module must ship alongside the code that imports it. When a hosting provider is configured to deploy only the `server` directory, anything outside that directory never reaches the container, and the application crashes at startup with:

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../shared/allocation.js'
```

Keeping the module under `server/` guarantees it is always present at runtime, while the client still imports the identical file at build time.

**Rule to follow:** nothing under `server/` may import outside `server/`. Any `../../` import in that directory will work locally but break in production.

### State ownership

The server is authoritative. It produces the complete step history in a single response, so the client never needs to re-run the algorithm to move between steps — stepping backward and forward is a matter of indexing an array, which keeps the replayed state exact.

## Deployment

The repository root contains a `package.json` that exists solely so that build systems can detect and start the project without any additional dashboard configuration:

```json
"scripts": {
  "build": "cd server && npm install",
  "start": "node server/server.js"
}
```

The `build` step installs the server's dependencies and the `start` step launches the API. This works whether the service root is the repository root or the `server` directory, because `server/package.json` also defines its own `start` script.

For a host such as Railway, Render, or Fly.io:

1. Point the service at this repository.
2. Leave the build and start commands at their defaults, or set them to the two scripts above.
3. Set the environment variables listed in [Environment Variables](#environment-variables), including `MONGODB_URI` if you want history persistence.
4. Make sure the platform's Git integration actually has access to the repository — a revoked integration is the most common reason a deployment silently keeps rebuilding an old commit.

When deploying the front end separately, set `VITE_API_URL` to the public URL of the deployed API, and set `CLIENT_URL` on the API to the public URL of the front end so that CORS permits the request.

## Limitations

- There is no authentication or user account system; the project is intended for local use and demonstration.
- History persistence is disabled unless MongoDB is configured, and the interface does not currently include a history browser.
- Comparison between algorithms is manual: run each one and compare the statistics, or read the table in [Allocation Algorithms](#allocation-algorithms).
- Allocation runs to completion in a single request rather than streaming, so there is no live animation of an allocation in progress — the step control replays the finished result instead.
- The simulator models contiguous allocation only. It does not cover paging, segmentation, or memory compaction.
